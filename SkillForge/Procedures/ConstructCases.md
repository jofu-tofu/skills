# ConstructCases

**Input:** Target workflow/version, claim, quality profile, available examples, and the applicable PlanChange plan/version. Without a plan, include the assessment/comparison request, baseline requirements where applicable, and budget.
**Output:** A reusable suite and frozen execution plan linked to its governing plan/version, status not_executed; gaps remain explicit.

1. Read the target outcome, measurement specification and affected dependencies. Call [DesignMeasurement](DesignMeasurement.md) if a measure is new, changed, unsupported or outside its qualified scope. Separate routing, instruction compliance, task outcomes, and cost. A designed measure can support case construction; it cannot yet certify skill improvement.
2. Include representative tasks, boundaries, and meaningful regressions. For changes to failure handling or evidence propagation, separate evidence for the outcome from overall execution status. Where applicable, cross sufficient versus absent/insufficient evidence with successful versus unsuccessful execution, and derive each expected verdict from the criterion. Include a contrast where a criterion is established before a later failure and one where it never becomes established; exercise the affected entry point and consumers. Do not require overall completion for a criterion that the available evidence already establishes, or assume partial output is sufficient without checking it. Label synthetic cases. Assign development, validation, or acceptance roles.
3. Use [Schemas](../Standards/Schemas.md) for evals.json and evaluation-plan.json. Materialize assertion IDs, judge evidence, snapshot identities and trials. Inherit baseline policy, decision rules, budget and stopping conditions from [PlanChange](PlanChange.md). Return conflicts or required policy changes to PlanChange for an explicit versioned amendment before freezing execution details. When no applicable plan exists, call PlanChange for the requested assessment or comparison policy; this authorizes no execution.
4. Keep executor inputs separate from grader-only answers. Materialize the specification's qualification contrasts and benchmark separately. Record checks on independently established passing/failing artifacts, valid alternatives and misleading passes when execution is authorized; otherwise preserve pending status. Update qualification evidence in the owned measurement record, not by assertion. Read [Grader](../Standards/Grader.md); load [Comparator](../Standards/Comparator.md) and [Analyzer](../Standards/Analyzer.md) only for judgment comparisons.
5. For a fix claim require baseline reproduction, predicted repair, preservation checks, and fresh cases where broader claims are intended. No-skill comparisons must exclude the target skill.
   For changed conditional steps, exercise the caller as well as the component. Include an applicable case where the optional work is unnecessary and its dependency is absent, and contrast it with work that genuinely requires the missing dependency. A stub that supplies every dependency cannot establish the absent-dependency path. Derive expected completion or blocking from the target contract; do not require a particular implementation.
6. Map cases and reused evidence to the governing plan's regression coverage. Surface missing branches, handoffs and nonapplication contrasts before execution; return material scope conflicts to PlanChange rather than silently shrinking the claim. Return coverage, justified exclusions, unavailable prerequisites, suite paths and not_executed status. A case-only request stops here.

Acceptance: a separate executor can run the plan without inventing requirements. A small smoke suite does not justify general effectiveness. Version suite changes independently of target changes.

## Consolidating model checks

When a plan repeats the same context across compatible model checks, compare sharing that context before increasing scenario complexity. A compound workflow can exercise several requirements and their interactions; keep each requirement's observation and failure identifiable. Map the coverage before replacing separate runs. Keep cheap deterministic checks, red/negative cases and small diagnostics where they expose distinct failures or help locate them. Fewer tests or harder prompts alone are not improvements.

Do not combine comparison arms, development with reserved confirmation, or draws that must remain independent. Several assertions in one context are one execution, not independent trials. If a combined result is ambiguous, split the affected check for diagnosis and preserve the original result and added cost.

For a token-saving claim, compare actual total input plus output tokens for equivalent completed work, including retries, diagnosis and model grading; report cached input separately without subtracting it from total input. Keep unmeasured preparation costs and missing usage explicit. Prefer the simplest arrangement supported by preserved coverage and measured savings. Where checks already share context, do not assume further savings or require a new comparison by default. PlanChange owns the acceptance rule and trial budget.

Before freezing a behavioral suite, trace every required decision in PlanChange's experiment adequacy check to observable evidence. Include the affected caller and final consumer where a handoff can lose the result. Inspect prompts for answers or coaching that remove the behavior being tested. Preserve development diagnoses separately from fresh confirmation; a saturated case remains useful preservation evidence but is not a reason to repeat an uninformative comparison. Return missing decision coverage to PlanChange before executing a suite that cannot answer its question.
