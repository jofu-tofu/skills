# ComprehensiveImprovement

**Input:** Broad improvement request, target intent and supported task surface, existing criteria/evidence, and authority.
**Output:** A reviewed parent coverage inventory, baseline structural assessment, and an evolving sequence of evaluated rounds. A round decision is not a task-completion decision.

Use for broad, comprehensive, deep or whole-skill improvement, including portfolios. A request to improve a skill generally uses this path unless the user actually bounds the requested effect to a particular defect, component or maintenance change. “Start with an easy change” selects the first round, not the final scope. Explicit focused repairs, assessment, design-only and maintenance requests keep their existing proportional paths.

## Establish the parent scope before choosing rounds

1. Derive the supported task families and intended results from user intent, the skill's purpose, entry points, outputs and consumers. Inspect all primary workflows and their important dependencies, including early exits and missing capabilities implied by the purpose. Current files are evidence, not the definition of quality. For portfolios, keep each skill visible; one aggregate check per skill is insufficient.
2. Call EstablishQuality to decompose each family into observable outcomes where different consequential failures need different checks. Cover normal operation, boundaries, invalid/unavailable inputs, conflicting requirements, state/side effects and cross-component handoffs where applicable. Include valid alternatives and nonapplication. Record criterion sources, contributors, evidence methods and exclusions. Do not invent irrelevant failure modes or maximize the number of rows.
3. Challenge **scope completeness separately from outcome performance**: could all selected checks pass while an important supported task still fails? Compare the inventory against the original request and full task surface, not just the proposed experiment. Use a separate reviewer when available, otherwise an explicit second review pass. Preserve missing families and unresolved requirements as work. The reviewer must see the original request and target, not only the author's summary. Resolve scope omissions before freezing the parent contract; later newly discovered in-scope outcomes expand it through a recorded amendment rather than disappearing into limitations.
4. Before selecting edits, call ReviewDesign on the whole target: responsibility/rule ownership, entry routing, loading boundaries, dependencies, artifact schemas, composition, alternate routes and failure/recovery handoffs. Map findings to outcomes. Compare coherent structural alternatives—including retaining the structure—and prioritize changes that remove observed contradictions, missing ownership or interface obstacles. Structural consistency can be a directly checked benefit even if a capable model compensates for the old instructions; claim behavioral benefit only from applicable execution evidence. Do not require a big rewrite merely to demonstrate activity.

The parent inventory is a coverage contract, not a test script. Each outcome retains its status, qualification, evidence and remaining gap. Each target retains its structural-review status and findings. For comprehensive completion, use the inventory format in [Completion](../Templates/Improvement/Completion.md), or map an existing profile to it without duplicating its reasoning. Freeze it before round budgets and candidate edits. A reviewer approving a narrow round does not approve shrinking the parent.

## Run and reconcile successive rounds

5. PlanChange ranks material uncovered/uncertain outcomes and structural findings by consequence, evidence, dependencies and effort. Select the next useful round and name which parent outcomes it can resolve. A per-call or per-round resource bound limits that execution, not the requested task. Keep the remaining inventory/backlog visible. Research consequential unknowns where evidence could alter the approach.
6. Execute the round through DraftCandidate, ReviewDesign and EvaluateCandidate as applicable. A round may qualify a measure, evaluate a baseline, restructure a responsibility, repair behavior, or reject a needless change. Test the user-visible result and affected handoffs; preserve valid alternatives and relevant existing behavior. Record the actual effect, adverse results and limits. A component fix does not automatically establish all outcomes of its workflow.
7. Reconcile results with the **same parent inventory**. A passing case closes only outcomes it adequately exercises; a no-change decision has the same scope. Revisit the structure when failures reveal missing or conflicting responsibilities. Newly exposed same-purpose gaps remain required work. Rerank and execute another useful round whenever a material required outcome lacks adequate evidence or a structural finding remains unresolved. Do not repeatedly run saturated cases, invent more difficulty for a win, or demand a fixed number of rounds/edits.
8. Check completion against the parent through ApproveSkill, then RecordLearning. Completion requires adequate qualified evidence across the required inventory, resolved structural findings (including evidence-based rejection of a proposed change), and a final scope challenge against the original request. Honest unknowns are not passes. If a feasible authorized next step exists, continue it; a self-selected pilot limit or inconvenient remaining work is not a blocker. Genuine execution/authority/resource limits leave affected outcomes unresolved and require the actual blocked status and resume action.

Comprehensive means coverage of the supported domain and its consequential interactions, not proof over every possible input or permanent optimality. An already adequate skill can finish unchanged after sufficiently broad evaluation and structural review. Preserve design-only and user-approved exclusions explicitly; neither “finite tests cannot prove everything” nor “one case passed” justifies abandoning feasible required work.

## Durable results

Keep reusable outcomes, structural rationale, current coverage and the retained version in the target's existing quality/attempt records; raw runs can remain in an external workspace with stable references. Record round decisions separately from overall completion. A later run must recover unresolved work without treating a previous scoped pass as whole-skill readiness. Avoid boilerplate file migrations when existing records serve these roles.
